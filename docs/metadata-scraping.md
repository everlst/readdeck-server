# 元数据扫描与刮削

书库工具栏和设置页的“扫描并刮削”均只刮削已启用、可访问且开启“自动刮削”的来源，与启动及监听触发的自动刮削遵循相同范围。关闭自动刮削的来源仍会被扫描和索引；同一作品跨来源时，仅处理允许来源的卷册。批量强制刷新也不扩大来源范围，单本详情的“重新刮削”仍可明确处理关闭自动刮削的来源。

## 本地扫描

联网开启、关闭或 AI 不可用时，快速扫描、完整扫描和监听增量扫描均使用本地 `parseName` 与目录结构推断，不读取 AI 名称缓存、不发送 AI 请求、不等待 AI 队列。扫描完成后的自动刮削是独立阶段。

识别卷号、章节与父目录分组；无法判断时，直接包含图片的目录视为单话，子目录包含图片的目录视为卷册。扫描保留资源身份、首次索引时间及保存的刮削字段，目录图片的变更纳入资源指纹。非扫描阶段的候选提示、强制重建和设备描述继续使用单项 AI 名称解析与缓存。名称翻译仍按原批次执行，没有文件名批处理器。

扫描器、图片读取和文件监听统一忽略 `.sync`、`.stversions`、`.git`、`__MACOSX` 等工具目录。发现的新作品可提前显示；扫描失败时不删除旧资源。

## 主作品识别

需要全量刮削且联网开启时，内部 `workIdentification.identifyWork` 最多发起一次联网 AI 请求，返回 `{ subjectId, status, reason, evidence }`。提示词位于 `lib/workIdentification.js`，输入复用安全收集流程，仅含允许的本地元数据、原始名称和资源标识，排除路径、密钥、正文与阅读进度。

按用户约定，程序直接使用 AI 返回的正整数 ID，不核验搜索证据，也不预先比对 Bangumi 条目。证据只作为诊断记录。该 ID 作为内部识别结果进入共享传统详情链，不标记为人工指定。程序读取 Bangumi 详情、关联、人物、封面与卷册；后续 AI 只做普通名称解析、翻译和可选语义匹配，不联网检索译名。

识别无法返回可用 ID、JSON 无效或请求失败时，直接转入传统候选召回，不重试联网识别。联网和传统召回都失败时，只有没有旧结果的作品可以保存本地回退。独立“测试联网搜索”仍检查真实工具调用与官方来源，用于检测接口能力。

传统候选召回合并 AI 建议词与本地标题，最多使用 12 个检索词，每词读取 Bangumi API 的前 20 条结果。每次搜索限时 15 秒，网络错误、HTTP 408/429/5xx 和无效响应最多尝试 3 次，重试间隔为 0.5 秒、1 秒；其他 HTTP 错误直接记录失败并继续。日志记录检索词、尝试次数、HTTP 状态和底层错误原因，某个词失败不丢弃此前结果，也不跳过后续检索词。

所有已返回的 API 候选与离线召回候选（最多 300 条）按 subject ID 去重，完整交给 AI，不再截取前 12 条或按规则分数筛选。搜索响应已包含简介、作者与 infobox，候选阶段不再逐项请求详情；AI 完成形态、标题和主系列判决后，其选择的候选 ID 直接进入详情、人物、关联及卷册流程。人工指定和已有结果保护仍沿用上述规则。

存在失败检索词且没有可靠匹配时，报告网络或搜索请求失败，说明检索不完整；全部检索成功但没有候选或 AI 拒绝全部候选时，报告“搜索成功但无可信匹配”。部分词失败而其他候选或离线候选被 AI 选中时，继续刮削。

新结果不再生成完整 `webScrape`。旧结构继续用于展示与兼容读取，包括没有数字 ID 的作品、来源链接与卷册详情。

## 已有结果保护

完整、部分和已持久化的本地回退均属于已有结果；单纯扫描索引不属于刮削结果。模式切换、策略版本过旧、详情缺失或单独传入 `refreshMetadata` 均不允许覆盖已有结果。没有资源变化时直接复用，不重写磁盘 bundle 或原来的 `scrapeMode`。

新增或变化资源通过与模式无关的资源指纹和扫描增量记录定位，只补充对应资源；旧主作品、来源、简介、人物、关系和卷册详情保持不变。旧记录缺少指纹不触发整项重刮。旧联网结果有正整数 `subjectId` 时使用传统卷册链；没有可用 ID 时保留结果，等待强制重刮或人工指定。

设备描述的相同输入结果跨模式与版本复用，包括旧任务、部分结果、本地回退及重启恢复。精确书名、明确作者和资源类型相同的设备卷册可复用主作品上下文。

只有显式 `force` 跳过旧结果、名称缓存、共享刮削缓存和增量保护。新结果准备成功后完整替换，失败保留旧结果。人工指定 ID 使用现有强制入口。只有成功写入新的全量结果时更新 `scrapeMode`。

## AI 发送调度

单个服务进程中，普通生成、联网搜索和连接测试共用一个队列。相邻请求实际发送至少间隔固定 **3000ms**，并受现有 AI 并发设置限制；模型列表和 Bangumi 请求不受此间隔影响。

等待发送不占用在途名额，超时从实际发送开始。并发数为 4 时，长请求可在第 0、3、6、9 秒依次启动。空闲不积攒额度，优先级提升、请求完成和提高并发都不能造成集中发送。降低并发允许旧请求完成，直到在途数低于新上限再发送。

队列使用单调时钟和统一唤醒定时器，保留优先级、请求合并和调用上下文。缓存命中、合并调用不额外占发送名额；失败后的下一次 AI 请求仍受间隔约束。

## 验证

`npm test` 运行全部服务端测试。普通集成测试仅加速队列时钟，HTTP 超时仍用真实时间；`ai-scheduling-test.js` 单独使用可控时钟及默认真实 3 秒时钟。扫描一致性、旧结果保护、直接 ID 识别、传统详情链、强制失败保留、设备缓存和旧结构展示均有回归覆盖。
